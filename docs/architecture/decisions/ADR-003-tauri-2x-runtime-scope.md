# ADR-003: Tauri 2.x runtime scope is distinct from capability scope and plugin configuration — populate `app.<plugin>_scope()` programmatically at app setup

**Status:** Accepted (2026-05-10) — partially supersedes ADR-002 invariant 4
**Date:** 2026-05-10
**Decision drivers:** Story 1.11 (commit c626ea1) successfully migrated `tauri.conf.json` from Tauri 1.x permission schema to the 2.x capability model and unblocked `bun run tauri` boot. Manual smoke testing on the same evening (2026-05-10) surfaced a class of defects that ADR-002's invariant 4 ("hard separation between plugin configuration and plugin permissions") did not anticipate: the Tauri 2.x scope architecture is **three-way**, not two-way. Every `commands/fs.rs::fs_*` IPC command was returning `Err("path not allowed")` for in-allowlist paths because the runtime scope object queried by `app.fs_scope()` was empty — capability `fs:scope` entries do not populate it. This ADR locks in the three-way understanding and the canonical mechanism for populating the runtime scope, before Epic 02 (design system) or Epic 04 (plugin host SDK) compounds the gap.

## Context

ADR-002 §4 established that Tauri 2.x splits **plugin configuration** (in `tauri.conf.json plugins.<name>` blocks) from **plugin permissions** (in `capabilities/<name>.json` files). That separation is real and remains in force. What ADR-002 missed — because the failure mode only surfaces at runtime, not at boot or schema validation — is a **third concept**: the **plugin runtime scope state**, an in-memory mutable object owned by the plugin and accessed via a plugin-specific extension trait method.

For `tauri-plugin-fs` v2.5.1 the runtime scope object is `tauri::fs::Scope` and the accessor is `app.fs_scope()` (provided by the `FsExt` trait via `tauri_plugin_fs::FsExt`). Reading the plugin source confirms three behaviors that materially affect this codebase:

1. **The plugin initializes the runtime scope to empty at setup.** `tauri-plugin-fs/src/lib.rs:484-509` constructs `tauri::fs::Scope::new(app, &FsScope::default())` inside its `setup` closure. `FsScope::default()` is the empty configuration. **No allow paths, no deny paths.**
2. **Capability `fs:scope` entries do NOT populate the runtime scope.** Capability `fs:scope` data lands in `RuntimeAuthority.scope_manager.global_scope["fs"]` (tauri-2.11.1 `src/ipc/authority.rs:182-188`) and is consumed by the **plugin's built-in IPC commands** (e.g., `tauri-plugin-fs/src/commands.rs::read_file` extracts `global_scope: GlobalScope<Entry>` per call). It is a **separate scope storage** from `app.fs_scope()`.
3. **The runtime scope is the scope that `tauri-plugin-dialog` mutates** when a user picks a file — `dialog/src/commands.rs:163-254` calls `tauri_scope.allow_file(&path)` / `tauri_scope.allow_directory(&path)` after each pick. It is also the scope that `tauri-plugin-fs`'s own drag-drop handler mutates (`fs/src/lib.rs:510-526`). It is the canonical Tauri 2.x scope for any code path that uses `commands/fs.rs::fs_*`-style custom IPC wrappers checking `app.fs_scope().is_allowed(...)`.

This codebase's `commands/fs.rs::fs_read_file` (and three siblings) was authored against `app.fs_scope().is_allowed(...)` per Story 1.7 and reinforced by Story 1.10 — both stories pre-dated the capability-model migration. After Story 1.11 stripped the 1.x `plugins.fs.scope` block from `tauri.conf.json` (because the 2.x `Config` schema rejects it) and added a `fs:scope` capability permission per the auto-generated schema's example, the runtime scope had no source of truth populating it. The Story 1.7/1.10 code path was checking against an empty scope, denying every path. Smoke Test 7's apparent "DENIED_AS_EXPECTED" result for `/etc/passwd` was a false positive — the deny was correct by coincidence; the same mechanism was denying `~/.claude/CLAUDE.md`.

The fix is structural: populate `app.fs_scope()` at app setup with the same canonical allowlist declared in the capability file. This decision documents the three-way scope model, names the mechanism for populating the runtime scope, and establishes the source-of-truth discipline between the capability file and the Rust setup code.

## Decision

**Adopt the three-way Tauri 2.x scope model with the following five invariants:**

1. **Three distinct scope concepts.** Every Tauri 2.x plugin has up to three independent layers, each with its own location, semantics, and lifetime:
   - **Plugin runtime configuration** — fields the plugin's `Config` struct deserializes from `tauri.conf.json plugins.<name>`. Examples: `plugins.fs.requireLiteralLeadingDot`, `plugins.deep-link.desktop.schemes`, `plugins.shell.open`. Read once at plugin init; never mutated. **Authoring rule**: include only fields the plugin's `Config` struct accepts on the installed version. For plugin-fs v2.5.1, that means `requireLiteralLeadingDot` only — no `scope`, no method-permission booleans, no validators.
   - **Plugin capability permissions** — IPC-dispatch ACL entries in `capabilities/<file>.json`. Gate which IPC commands the webview is allowed to invoke and what scope arguments those invocations may carry. Consumed by Tauri's authority layer **before** the plugin's IPC handler is called. For permissions with a "scope" semantics (e.g., `fs:scope`), the entries land in `RuntimeAuthority.scope_manager.global_scope[plugin]` and are visible to the plugin's built-in command handlers via the `GlobalScope<T>` extractor. **Authoring rule**: enumerate against `gen/schemas/desktop-schema.json` (ADR-002 §2 unchanged); for scope-bearing entries, document the canonical allowlist here as the source of truth.
   - **Plugin runtime scope state** — an in-memory mutable object the plugin owns, accessed via a plugin-specific extension trait method on the `Manager` / `AppHandle` (e.g., `app.fs_scope()` from `tauri_plugin_fs::FsExt`, `app.shell()` from `tauri_plugin_shell::ShellExt`). Populated programmatically at app setup or dynamically by user actions (file pickers, drag-drop). Consumed by **custom Rust IPC commands** that bypass the plugin's built-in commands and any other Rust code that calls the scope's predicates (`is_allowed`, `allowed_patterns`). For plugin-fs, this is `tauri::fs::Scope` and the mutators are `allow_directory(path, recursive)`, `allow_file(path)`, `forbid_directory`, `forbid_file`. **Authoring rule**: if a custom Rust IPC wrapper checks `app.<plugin>_scope().is_allowed(...)`, the scope must be populated at setup; the capability file does not populate it.

2. **Runtime scope is populated programmatically in `lib.rs::run()` `.setup(|app| { ... })`.** For `tauri-plugin-fs` v2.5.1, the canonical mechanism is `app.fs_scope().allow_directory(path, recursive)?` for each path in the canonical allowlist, with paths resolved via `app.path()` (`home_dir()`, `app_data_dir()`, `app_dir()`). Variable-prefixed shorthand (`$HOME`, `$APPDATA`, `$APP`) is **not** valid in `allow_directory` — it is a capability-file convenience. Rust code resolves the variables via the `app.path()` API, which is the same resolver Tauri uses internally for capability-file expansion, guaranteeing physical-path equivalence on every supported platform.

3. **Source-of-truth discipline: capability file is canonical; setup code mirrors it.** The list of allowed paths is documented in `capabilities/<file>.json` as the security-review surface. `lib.rs::run().setup` resolves the same semantic paths via `app.path()` and registers them on the runtime scope. Sync between the two is enforced by:
   - A Rust integration test that asserts `app.fs_scope().is_allowed(<canonical-path>)` returns true for every entry in the canonical list (Story 1.12 §G).
   - A documenting comment block at the setup-code site naming the capability file as the source of truth.
   - Optionally a `CANONICAL_FS_ALLOWLIST: &[&str]` constant array near the setup-code site for visual cross-reference.
   - **Rationale for two source locations rather than one**: Tauri 2.x does not expose a clean public API to read capability `fs:scope` entries from Rust at app setup time. The data is buried inside `RuntimeAuthority.scope_manager.global_scope["fs"]`, and the typed accessor (`GlobalScope<T>`) only works inside command-handler scope-extraction. A "single source of truth" approach would require reflective access to plugin-internal types and would couple this codebase to Tauri-internal API stability. The two-source approach with a regression test is the simplest design that meets the discipline.

4. **Custom Rust IPC command wrappers use the runtime scope for defense-in-depth, not the capability scope.** When a custom command like `commands::fs::fs_read_file` checks the FS allowlist, it uses `app.fs_scope().is_allowed(...)` (runtime scope), not `GlobalScope<tauri_plugin_fs::scope::Entry>` (capability scope extracted via the IPC machinery). Rationale:
   - The runtime scope is where every other 2.x code path converges — file picker mutations, drag-drop, future dynamic project-open extensions (FB-015 Sprint 2 carryover).
   - `GlobalScope<T>` couples the command signature to plugin-internal types (`tauri_plugin_fs::scope::Entry` is `pub` but its shape across plugin minor versions is not contractually stable).
   - The runtime scope is the scope a security reviewer can inspect via `app.fs_scope().allowed_patterns()` at runtime to audit the live state of the allowlist; the capability scope state is harder to inspect at runtime.

5. **Capability `fs:scope` entries are retained even when no plugin built-in command is JS-exposed.** They serve as the documented source-of-truth allowlist (invariant 3) and as the IPC-dispatch gate for any future story that exposes a plugin built-in command (e.g., if Epic 04 plugin host SDK chooses to call `tauri-plugin-fs`'s built-in `read_file` IPC handler from JS rather than going through `commands::fs::fs_read_file`). Removing the entries because they appear "unused" by current commands would dismantle the documentation and the future-IPC-dispatch gate at the same time.

## Consequences

**Positive:**

- The boot is correct end-to-end: capability gating works at IPC dispatch (ADR-002 invariant 2 unchanged), runtime scope is populated at setup, custom Rust commands check the populated runtime scope, and the security signal (`fs-allowlist` violation log) fires on real denies and not on every call.
- The three-way model is explicitly named, removing the ambiguity that allowed Story 1.11 code review to answer "is this the canonical 2.x pattern?" with a wrong "yes." Future capability-related code reviews can check all three layers.
- Single explanation point for any future plugin runtime-scope concern. When Epic 03 adds an indexer-driven file watcher or Epic 04 adds a plugin SDK with its own per-plugin FS scope, the addition follows invariant 2 (programmatic init in setup) without re-deriving the architecture.
- Audit observability: `tracing::info!` on `fs-scope-init` at boot lists every allowed path with its resolved physical path, making the live scope state visible in default log configurations.
- Regression net via Story 1.12 §G integration test: any future refactor that drops the runtime-scope-init call breaks the test, surfacing the regression at `cargo test` time rather than at the next manual smoke test.

**Negative:**

- One additional file (`lib.rs`) is part of the security-review surface. The capability file remains the primary security document, but a reviewer must also verify that `lib.rs::setup` registers the same paths. Mitigated by the §3 comment block, the optional constant array, and the regression test.
- Adding a new allowed path requires touching two locations (`capabilities/default.json` + `lib.rs::setup`). This is the explicit cost of invariant 3's two-source design. Mitigated by the regression test catching out-of-sync states.
- The `withGlobalTauri: true` setting documented in Story 1.12 §F is a bounded but real security loosening, justified for Sprint 1 dev ergonomics and revertible before v0.1.0-alpha. Not strictly an ADR-003 concern, but the ADR's existence makes the revert path mechanical (capability scope and runtime scope both remain enforcing regardless of `withGlobalTauri`'s value).

**Neutral:**

- The dead-code observation about `shell:allow-execute` args validator (Story 1.12 §H research note) is a property of `tauri-plugin-shell`'s internal trust model, not of this ADR. Documented in the story, not in the ADR, because it is a single-plugin observation rather than a cross-cutting architectural pattern.
- ADR-003 does not introduce per-window or per-feature capability splitting — ADR-002 §1 (single capability file at `capabilities/default.json`) remains in force. If a future plugin-host story splits capabilities per loaded plugin, that story will need to re-evaluate whether its per-plugin runtime scope (if any) lives in the host's `setup` or in each plugin's own initialization.

## Alternatives Considered

**Alternative A — single source of truth = capability file; load it at setup via reflection.** Rejected: requires reading `RuntimeAuthority.scope_manager.global_scope["fs"]` at setup time, which is not a public Tauri API surface (the `RuntimeAuthority` type is `pub` but `scope_manager` is `pub(crate)` in tauri-2.11.1). Building this would couple the codebase to Tauri internals that are not contractually stable. The two-source-with-test discipline is simpler.

**Alternative B — switch custom Rust commands to extract `GlobalScope<Entry>` (capability scope) and abandon `app.fs_scope()`.** Rejected: couples the command signatures to `tauri_plugin_fs::scope::Entry`, a `pub` but minor-version-volatile type. Also abandons the convergence point that `tauri-plugin-dialog`'s file picker auto-mutates and that future drag-drop or project-open dynamic additions land in. The runtime scope is the right convergence point.

**Alternative C — use a plugin-builder pattern: `tauri_plugin_fs::Builder::default().scope(|s| { s.allow_directory(...) }).build()` in `lib.rs::run()`.** Rejected: not available on `tauri-plugin-fs` v2.5.1. The crate exposes `tauri_plugin_fs::init()` only; there is no public `Builder` type with a `.scope()` method on this version. If a future plugin-fs minor version adds a builder API, ADR-003 invariant 2 will be re-evaluated and a follow-up amendment may switch to the builder pattern as the canonical mechanism (one-line refactor against the helper function this story extracts).

**Alternative D — pre-populate the scope by extracting `FsScope::Scope { allow, deny }` config from a Rust constant and constructing a custom `tauri::fs::Scope::new(app, &my_fs_scope)?` in setup, bypassing the plugin's empty-default initialization.** Rejected: the plugin still owns the `Scope { scope: tauri::fs::Scope }` managed state via its own `app.manage(scope)` call inside its `setup` closure (`tauri-plugin-fs/src/lib.rs:506`). Constructing a parallel `tauri::fs::Scope` in our `setup` would not replace the plugin's stored scope — `app.fs_scope()` would still return the plugin's empty one. The only way to mutate the plugin's stored scope is to grab the existing handle via `app.fs_scope()` and call its mutators. Invariant 2 is therefore not just "the canonical pattern" but also "the only working pattern" on this plugin version.

## Implementation Impact

**Story 1.12 implements this ADR.** Subsequent plugin additions and FS-related stories must:

1. **Adding a new permanent allowed path**: Add the path to `capabilities/default.json fs:scope.allow` AND register it in `lib.rs::run().setup` via `app.fs_scope().allow_directory(resolved_path, recursive)?`. Update or extend the §G regression test to assert the new path is in scope.
2. **Adding a dynamic allowed path** (e.g., FB-015 active-project-path Sprint 2 carryover): Mutate `app.fs_scope().allow_directory(...)` at the point the dynamic event fires (project-open handler). Add a `fs:scope` capability entry **only if** the path is also needed by the plugin's built-in IPC commands (currently none are JS-exposed); for paths consumed only by `commands/fs.rs::fs_*`, the runtime mutation alone is sufficient.
3. **Adding a new plugin with a runtime-scope concept** (e.g., `tauri-plugin-http` adding URL scope, `tauri-plugin-store` adding key-prefix scope): Verify the plugin's runtime-scope mechanism by reading the crate's `lib.rs::init`. If the plugin initializes its scope to empty at setup and exposes mutators, follow invariant 2's pattern in `lib.rs::run().setup`. Add a one-line note to ADR-003 §"Implementation Impact" naming the plugin and its scope mechanism.
4. **Reviewing a capability-related PR**: verify all three scope concepts. Capability file lists the canonical allowlist. `lib.rs::setup` registers the same paths on the runtime scope. Custom commands check the runtime scope (not the capability scope).

**Inspecting the live scope state at runtime** (debugging / security audit): from a Tauri command or app event handler, call `app.fs_scope().allowed_patterns()` to get a `HashSet<glob::Pattern>` of all currently-allowed patterns. The set reflects setup-time registrations plus any runtime mutations from dialog file pickers, drag-drop, or future dynamic additions.

For future readers: the canonical 2.x scope-mutator API for `tauri::fs::Scope` is documented in `tauri-2.11.1/src/scope/fs.rs:176-372`. The capability `fs:scope` permission shape is documented in the auto-generated `src-tauri/gen/schemas/acl-manifests.json` under `fs.permissions.scope.description` (with the example pattern this codebase follows). The two are independent and ADR-003 §1 is the canonical statement of their relationship.
